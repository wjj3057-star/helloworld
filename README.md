# 문제집 스캐너

푼 문제집을 여러 장 찍어서 **선생님께 보낼 PDF 한 개**로 만들어 주는 웹앱입니다.

사진 30장을 카톡에 하나씩 올리는 대신, 찍고 → 자동 보정 → PDF 한 개로 공유하면 끝입니다.

- 종이 영역을 **자동으로 찾아 반듯하게 폅니다** (비스듬히 찍어도 됨)
- **그림자와 조명 얼룩을 지워** 글씨를 또렷하게 만듭니다 (빨간펜 채점 표시는 색 그대로 유지)
- 페이지 **순서를 바꾸고** 필요 없는 장은 지울 수 있습니다
- **PDF 한 개**로 묶어 카톡·메일로 바로 공유합니다

설치할 것도, 회원가입도, 서버도 없습니다. 사진은 **기기 밖으로 나가지 않습니다.**

## 안드로이드 앱(APK)으로 설치하기

저장소 **Releases → `apk-latest`** 에서 `workbook-scanner.apk` (약 2MB)를 받으면 됩니다.
폰 브라우저로 바로 열어 받아도 되고, 받은 뒤 눌러서 설치하세요.
(처음 설치할 때 한 번 "출처를 알 수 없는 앱 설치 허용"이 필요합니다.)

`index.html` 이나 `android/` 를 고쳐 푸시하면 APK가 자동으로 다시 빌드되어
같은 자리에 갱신됩니다. 직접 다시 굽고 싶으면 **Actions → APK 빌드 → Run workflow**.

### 서명 키 등록 (한 번만)

키를 등록하지 않아도 APK는 만들어지지만, **디버그 키는 빌드할 때마다 새로 생성**됩니다.
그러면 다음 APK가 안드로이드에게 "다른 앱"으로 보여서 **덮어쓰기 설치가 실패**합니다
(매번 지우고 새로 깔아야 함). 고정된 키를 등록하면 그냥 업데이트됩니다.

**Settings → Secrets and variables → Actions** 에서 아래 2개만 등록하면 됩니다.

| 이름 | 값 |
|---|---|
| `KEYSTORE_BASE64` | 키스토어 파일을 base64 로 바꾼 문자열 |
| `KEYSTORE_PASSWORD` | 키스토어 비밀번호 |

별칭은 `workbook` 이 기본값이고, 키 비밀번호는 따로 주지 않으면 키스토어 비밀번호를
그대로 씁니다. 다르게 쓰려면 `KEY_ALIAS` / `KEY_PASSWORD` 를 추가로 등록하세요.

키를 새로 만들려면:

```bash
keytool -genkeypair -v -keystore release.jks -alias workbook \
  -keyalg RSA -keysize 4096 -validity 10950
base64 -w0 release.jks     # 이 출력을 KEYSTORE_BASE64 에 넣는다
```

등록 후 다시 빌드하면 실행 요약에 `서명: 정식 키` 와 인증서 지문이 표시됩니다.

> `release.jks` 는 이 앱의 신분증입니다. 잃어버리면 기존 설치본을 덮어쓰는 업데이트를
> 만들 수 없습니다. 안전한 곳에 보관하고 **저장소에는 절대 올리지 마세요**
> (`.gitignore` 로 `*.jks` 를 막아두었습니다).

앱은 `index.html` 을 그대로 담은 얇은 껍데기입니다. 웹과 완전히 같은 코드가 돌아가며,
빌드할 때 루트의 `index.html` 이 자동으로 복사되므로 사본을 따로 관리하지 않습니다.

앱으로 쓰면 좋은 점:

- **인터넷 권한이 아예 없습니다.** 사진이 밖으로 나갈 수 있는 통로 자체가 없습니다
- 만든 PDF를 **안드로이드 공유 시트**로 넘겨 카톡·메일로 바로 보냅니다
- 주소를 몰라도 홈 화면 아이콘으로 바로 실행됩니다

> 웹에서는 `file://` 로 열면 브라우저가 카메라를 막습니다. 앱은 내부적으로
> `WebViewAssetLoader` 로 https 와 같은 조건을 만들어 주기 때문에 연속 촬영이 그대로 됩니다.

직접 빌드하려면 안드로이드 SDK를 갖춘 환경에서:

```bash
cd android && ./gradlew assembleDebug
# → android/app/build/outputs/apk/debug/app-debug.apk
```

## 웹으로 쓰는 법

`index.html` 파일 하나가 전부입니다. 브라우저로 열기만 하면 됩니다.

**휴대폰에서 쓰려면** GitHub Pages로 올려두고 주소를 즐겨찾기 해두는 게 가장 편합니다.

1. 저장소 **Settings → Pages → Source: `main` 브랜치 선택**
2. 잠시 뒤 나오는 `https://<아이디>.github.io/<저장소이름>/` 주소를 휴대폰에서 열기
3. 브라우저 메뉴에서 **홈 화면에 추가** 하면 앱처럼 쓸 수 있습니다

> 연속 촬영(카메라 바로 쓰기)은 브라우저 보안 정책상 **https 주소에서만** 동작합니다.
> 파일을 직접 열었을 때(`file://`)는 자동으로 휴대폰 기본 카메라 앱을 띄우는 방식으로 넘어갑니다.

### 작업 순서

1. **연속 촬영** — 셔터를 계속 눌러 여러 장을 이어서 찍습니다. 찍는 동안 뒤에서 알아서 보정됩니다.
   이미 찍어둔 사진이 있으면 **불러오기** 로 한 번에 여러 장 선택하면 됩니다 (파일 이름순으로 정렬됩니다).
2. 썸네일에서 순서를 확인합니다. `◀` `▶` 로 순서 변경, `🗑` 로 삭제.
3. 잘린 부분이 이상하면 썸네일을 눌러 **네 모서리를 손으로 끌어** 맞춥니다.
4. **PDF 만들기** — 공유 창이 뜨면 카톡·메일로 바로 보냅니다. (공유를 지원하지 않는 환경에서는 파일로 저장됩니다.)

### 설정 (⚙)

| 항목 | 설명 |
|---|---|
| 파일 이름 | `수학문제집_2026-07-25.pdf` 처럼 저장됩니다 |
| 최대 용량 | 메일 첨부 제한 등에 맞춰 여러 개로 나눠 저장합니다 (`0` = 나누지 않음) |
| 기본 보정 | **문서**(기본) / **흑백 강조**(글씨 진하게) / **원본**(보정 안 함) |
| 화질 | 가벼움 / 보통 / 선명 |

작업 중인 페이지는 브라우저에 자동 저장되어, 실수로 창을 닫아도 다시 열면 그대로 남아 있습니다.

## 어떻게 동작하나

외부 라이브러리 없이 전부 직접 구현되어 있습니다 (`index.html` 한 파일).

1. **종이 찾기** — 임계값 하나로 자르면 그림자 진 모서리가 잘려 나가거나 책 접힘부에서
   페이지가 두 조각으로 갈라집니다. 그래서 여러 후보를 만들어 놓고 가장 그럴듯한 것을 고릅니다.
   - 밝기와 **"종이다움"**(밝고 채도 낮은 정도) 두 채널에 대해, Otsu 임계값과 그보다 낮은
     여러 임계값으로 후보 마스크를 만듭니다 (거의 같은 마스크는 건너뜁니다)
   - **닫힘 연산**(팽창 후 침식)으로 접힘부 그림자 같은 가느다란 틈을 메워 한 덩어리로 만듭니다.
     적분영상을 써서 반지름과 무관하게 픽셀당 O(1)입니다
   - **흰 종이를 흰 책상에 놓으면 밝기로는 나눌 수 없습니다.** 임계값을 어디에 두든 둘이
     같은 쪽으로 묶입니다. 이때는 밝기 대신 **"기울기가 큰 곳"을 선으로 보고**, 끊긴 곳을
     메운 뒤 화면 테두리에서 물을 부어 **잠기지 않는 안쪽**을 종이로 봅니다. 종이 두께가
     만드는 미세한 그림자만 있으면 되므로 종이가 더 밝든 어둡든 똑같이 동작합니다
   - 결이 있는 책상(나뭇결·천·광택 얼룩)에서는 문턱을 어디에 둬도 안 됩니다. 낮추면 책상
     전체가 선으로 막혀 물이 못 들어가고, 높이면 흐린 종이 테두리가 끊깁니다. 그래서 한 번 더,
     **크게 뭉갠 그림으로** 같은 일을 합니다. 노이즈는 뭉개면 사라지지만 종이 그림자는
     몇 픽셀 폭이라 살아남습니다
   - 8-이웃으로 가장 큰 덩어리를 잡고, **볼록껍질**에서 **넓이가 최대인 사각형**을 고릅니다
   - 각 변에 놓인 경계점 전체를 **최소제곱 직선으로 근사한 뒤 이웃 직선을 교차**시켜
     꼭짓점을 다시 구합니다 → 손가락이나 잡티 하나에 모서리가 끌려가지 않습니다
   - 채움·포함·경계 강도(소벨)·면적·안팎 밝기 단차로 점수를 매겨 최종 후보를 고릅니다
   - **종이가 아닌 게 확실한 후보는 만들자마자 버립니다.** 화면을 다 덮는 것, 경계도 단차도
     없는 것, 변 안쪽이 바깥보다 한참 어두운 것(= 종이 테두리가 아니라 글씨 한가운데에
     선을 그은 것). 끝에 가서 버리면 늦습니다 — 그때까지 "제일 좋은 후보" 자리를 차지하고
     앉아, 뒤에 올 다른 방식들이 "이미 답이 있다"며 아예 돌지 않기 때문입니다
   - 경계 기반 경로에는 조건이 하나 더 붙습니다. **변이 진한 경계 위에 놓인 후보는 버립니다.**
     이 경로는 흐린 종이 테두리를 찾으려고 있는 것이고, 진한 경계를 따라 만들어진 사각형은
     십중팔구 **글씨 덩어리의 외곽**입니다 (진짜 종이였다면 밝기 기반이 이미 찾았습니다)
2. **펴기** — 그 사각형을 직사각형으로 보내는 호모그래피를 8×8 연립방정식으로 풀고,
   결과 픽셀마다 원본을 역방향으로 이중선형 보간해 채웁니다.
3. **비율 복원** — 변 길이 평균만 쓰면 원근에 눌린 비율이 그대로 남습니다.
   직사각형이라는 조건(`b1·b2=0`, `|b1|/|b2|`=비율)에서 초점거리를 역산해 실제 종이 비율을 되살립니다.
4. **그림자 제거** — 적분영상으로 국소 평균 밝기(=종이 배경)를 구한 뒤 나눠 줍니다.
   채널마다 같은 배경값으로 나누기 때문에 **빨간펜 같은 색은 색을 유지**합니다.
5. **PDF 생성** — JPEG를 `DCTDecode` XObject로 넣어 PDF 1.4 구조(xref 테이블 포함)를 직접 씁니다.

### 연속 촬영이 안 끊기는 이유

셔터를 누른 뒤 화면이 멎으면 다음 장을 못 찍습니다. 그래서 **메인 스레드가 사진
픽셀을 한 번도 만지지 않게** 만들어 두었습니다.

| 하던 일 | 예전 | 지금 |
|---|---|---|
| 미리보기에서 한 컷 뜨기 | 캔버스에 그리기 145ms + JPEG 굽기 1.4초 | 프레임 워커가 처리 (메인 0ms) |
| 워커로 넘기기 | JPEG 로 구웠다가 워커가 다시 풂 | 비트맵을 복사 없이 넘겨줌 |
| 목록 다시 그리기 | 매번 전부 새로 만듦 | 바뀐 카드만 고침 |

`MediaStreamTrackProcessor` 로 카메라 프레임을 워커에 직접 흘려보내면, 셔터를
누를 때 메인 스레드가 하는 일은 "지금 한 장"이라고 말하는 것뿐입니다.
JPEG로 구웠다가 다시 푸는 왕복도 통째로 없어져서 처리량도 같이 올라갑니다.
쓸 수 없는 브라우저에서는 예전 방식으로 자동으로 넘어갑니다.

합성한 시험 이미지(기울어진 종이 + 조명 얼룩)로 측정한 결과입니다.

**종이 자동 감지** — 실제 촬영 상황 14가지를 1080×1440 으로 합성해 정답 꼭짓점과 비교했습니다.

| 조명 얼룩 심함 / 한쪽 깊은 그림자 | 4.5px | **4.0px** |

종이와 책상의 밝기 차이를 단계별로 줄여 가며, 그림자 유무·광택 반사·책상 질감까지 넣었습니다.

| 장면 | 이전 | 지금 |
|---|---|---|

| 그림자 없음 | 0.4px | **0.4px** |
| 거의 동일 밝기 | 6.5px | **6.5px** |
| 비뚤게 + 저대비 | 5.1px | **5.1px** |
| 책상이 더 밝음(조명) | ❌ 아무것도 못 찾음 | **16.0px** |
| 광택 책상 반사 | ❌ 아무것도 못 찾음 | **17.1px** |
| 질감 있는 흰 책상 | ❌ 아무것도 못 찾음 | **8.8px** |

못 찾던 세 장면은 원인이 둘이었습니다.

- **쓰레기 후보가 자리를 차지하고 앉아 있었습니다.** 화면의 99%를 덮는(=자를 것이 없는)
  후보가 점수 3.0을 받아 "제일 좋은 후보"가 되는 바람에, 뒤에 올 다른 방식들이 "이미 답이
  있다"고 판단해 아예 돌지 않았습니다. 어차피 마지막에 버릴 후보였는데 버리는 시점이
  늦었던 것입니다. → **만들자마자 버리도록** 옮기니 책상이 더 밝은 경우가 살아났습니다.
- **결이 있는 책상에서는 경계 문턱을 어디에 둬도 안 됐습니다.** → 크게 뭉갠 그림으로
  한 번 더 훑게 했습니다. 이때 나온 정답 후보는 점수 2.90으로 오답(2.47)을 이기고 있었는데
  **"테두리가 이어지는 정도" 조건에 걸려 버려지고 있었습니다.** 재 보니 진짜 종이가 0.46~0.71,
  글씨 덩어리가 0.82로 **오히려 뒤집혀 있어** 이 지표로는 둘을 가릴 수 없었습니다.
  대신 **경계 강도**가 깨끗하게 갈랐습니다(종이 0.22~0.54 / 글씨 덩어리 1.00). 조건을
  바꾸니 7/7이 됐습니다.

> (원래 벤치 파일이 작업 환경 초기화로 사라져 새로 만들었기 때문에, 그 이전 커밋 메시지에
> 적힌 수치와는 장면이 달라 직접 비교되지 않습니다.)

종이가 없는 사진(균일한 배경 등)에서는 아무 사각형도 내놓지 않고 원본을 그대로 씁니다.
감지에 걸리는 시간은 대비가 뚜렷한 보통 사진에서 한 장당 **50~60ms**,
밝기로 구분되지 않는 흰-흰 상황에서만 경계 기반 경로가 더 돌아 **130~220ms** 입니다.
어느 쪽이든 워커에서 도는 일이라 촬영 중 화면에는 영향이 없습니다.

**연속 촬영 중 화면 멎음** — 보급형 폰에 맞춰 CPU를 4배 느리게 만든 상태에서,
가짜 카메라로 셔터를 눌러 가며 프레임 간격을 쟀습니다. (60fps = 17ms가 정상값)

브라우저가 "화면이 멈췄다"고 보는 기준(50ms 넘는 작업)에 걸리는 일이 **0건**입니다.
보통은 프레임 예산(17ms)을 1~2ms 넘는 정도이고, 한 세션에 몇 번 10ms 넘게

## 알아둘 점

- **흰 책상 위의 흰 A4**를 기준으로 맞춰 두었습니다. 어두운 책상은 물론 더 잘 됩니다.
  다만 종이가 화면 밖으로 잘려 나가면 테두리가 닫히지 않아 놓칠 수 있습니다
  (이때는 자르지 않고 원본을 그대로 씁니다).
- 종이가 화면을 거의 꽉 채우면 자를 것이 없다고 보고 그대로 씁니다.
- 자동 감지가 빗나가면 썸네일을 눌러 **직접 모서리를 맞추면** 됩니다. (`자동 감지` / `전체 사용` 버튼도 있습니다)
- 아주 심하게 기울여 찍으면 글씨가 뭉개집니다. 가능하면 위에서 반듯하게 찍는 게 좋습니다.
